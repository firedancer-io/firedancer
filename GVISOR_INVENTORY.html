Bottom line

Firedancer boots and runs real workloads under gVisor today with (a) a handful of bundle/host-side accommodations and (b) an LD_PRELOAD shim that papers over six gVisor gaps. Proven end to end on tsewr2-ossdev-firedancer8 (Rocky 9.7, 96 cores, runsc release-20260817.0, branch mmcgee/scheduler-waker-tile build):

  • udpecho mini-topology (net/metric/l4swap tiles): full boot → tile spawn → UDP request in on the veth, swapped reply out, captured with tcpdump.
  • backtest with the real dump/mainnet-424669000-perf-ledger config: 39+ workspaces created (incl. the 63 GiB accdb workspace, fully mlocked), all tiles spawned (snapct/snapdc/snapin/snapwr/replay/execrp×10/backt/tower/diag/…), snapshot tar streamed through snapct→snapin. The final stop is a branch/fixture mismatch, not gVisor: this branch's manifest parser caps FD_RUNTIME_MAX_VAT_VOTE_ACCOUNTS at 2000 while the May-era snapshot has 6814 vote accounts in versioned epoch stakes (fd_ssmanifest_parser.c:1557). It would fail identically on bare metal; needs a branch-compatible fixture.
Every shim item in the inventory is a candidate for a tiny upstream fix if we want to drop the shim. None of them is architectural.

How to test (harness)

Everything lives in /opt/gvharness/ (self-contained, reboot-safe; sources included). No Docker required — plain runsc run with an OCI bundle.

FileRole
fdgv.shWrapper. Rewrites process.args in the bundle, creates the gvtest netns + veth pair if missing, re-applies the veth addr/route (runsc strips them on device takeover), runs runsc --overlay2=root:memory --net-raw run, deletes the container after. --flags "…" passes extra runsc flags.
config.jsonOCI spec. rootfs = host / with readonly:false + memory overlay (writes are discarded; host untouched). Binds: host /sys/devices/system ro (NUMA topology), /sys/kernel/mm ro, /mnt/.fd/.huge + /mnt/.fd/.gigantic rw, tmpfs on /tmp and /dev/shm. Network namespace /var/run/netns/gvtest (10.200.0.1 host ↔ 10.200.0.2 sandbox). rlimits set in-spec: NOFILE 1M, MEMLOCK ∞, NICE 40, STACK 8 MiB.
runscgVisor release-20260817.0 (sha512-verified from the release bucket).
align_mmap.c / .soLD_PRELOAD shim: aligned hugepage mmap, fake /proc/self/mounts, fake sysctl/proc files, MADV_WIPEONFORK→OK. Each behaviour is opt-in via an env var (see invocation).
fake_mounts, fake_sysctl/, fake_sched, fake_proc/Replacement contents for the procfs entries gVisor lacks.
gv.toml, gvbt.tomldev/udpecho and backtest configs carrying the gVisor-required knobs.
probe.c, poll_repro*.c, pivot_probe.cSyscall capability probes and minimal repros (results below).

Verified working — no action

  • fd_boot; shmem create/join/alloc/unlink on bind-mounted 2 MiB hugetlbfs via the gofer, including a 63 GiB workspace with full mlock population.
  • fd_tile threading (test_tile), tile spawn, prometheus HTTP server, tango links carrying real traffic, zstd snapshot streaming through the snapshot tiles.
  • The sandboxing primitives fd uses: seccomp-BPF, unshare(USER/NET/NS), the exact fd_sandbox pivot_root sequence, capget/capset, landlock (ENOSYS path).

Open items and risks

  • gVisor sentry panics on mlock over an under-provisioned hugetlb pool. With enough pages the 63 GiB mlock succeeds; without, the sentry crashes the whole sandbox (ExtractErrno "stub syscall (mmap) failed with cannot allocate memory", goroutine dump from sys_signal.go) instead of fd receiving ENOMEM — which fd would tolerate (fd_shmem_user.c:283 only warns). Worth filing upstream. The perfloop backend must provision nr_hugepages strictly ≥ topology demand.
  • io_uring is ENOSYS (runsc has an experimental --iouring). Only fd_snapsv (backup tile) uses it today — not in the dev/backtest/bench paths. Vinyl declares an io_uring IO type but it isn't built. Becomes relevant if accdb goes async-IO.
  • Multi-process boot (clone-per-tile with the full per-tile sandbox) was not exercised end to end — the default dev topology (~247 GiB) didn't fit beside the live validator. All its primitives probe green; backtest/udpecho use fd_topo_run_single_process, which is the perfloop-relevant path.
  • Overlay writes (accounts.db, logs, generated keys/genesis) live in sentry memory — size for it or bind a real scratch dir rw.
  • Performance was not characterised; this was a functional inventory. Known taxes: netstack UDP path, 208 KiB socket buffers, gofer-mediated page faults on the hugetlbfs files, no NUMA locality, KVM vs ptrace platform choice.

Host-side notes

  • Fixture prep for backtest: this branch's backt tile reads a shredcap pcapng, not RocksDB. Converted once with fd_blockstore2shredcap --rocksdb … --out … --zstd → dump/mainnet-424669000-perf-ledger/shredcap.pcapng.zst (1297 slots, 301 MB). gvbt.toml points at it. Its snapshot is incompatible with this branch's manifest cap (see bottom line) — a current fixture is needed for a complete run.
  • Always set a unique name. One early boot with the default fd1 unlinked and recreated the live validator's workspace files on the shared hugetlbfs mount. Harmless to the running process (POSIX unlink semantics) but it consumes pool pages and would confuse a restart. The harness configs pin gvtest/gvbt.
  • hugetlb reservation accounting on tsewr2-ossdev-firedancer8 was already underflowed on 2026-08-26 and worsened with each SIGBUS'd min_size reservation, pinning the 2 MiB pool at 48000 pages (94 GiB) until the box was rebooted on 2026-09-10. Pool is sane again (HugePages_Rsvd normal). Sandbox runs should keep min_size reservations within the pool to avoid re-triggering this.
  • Where things live now: the harness, runsc binary and bundle are all in /opt/gvharness (verified working 2026-09-13 with test_util_base on the mmcgee/benchcfg1 build at build/native/gcc/11.5.0/). Nothing under /tmp is required any more.

Recommendation for the perfloop backend

  1. Run via Docker/containerd with the runsc runtime (netns/veth, bundle and rlimits come for free); image contains the fd build and a non-root user in /etc/passwd.
  2. Bind the host 2 MiB hugetlbfs mount rw; skip the gigantic mount entirely. Provision nr_hugepages ≥ topology demand + slack before launch — the sentry panics rather than degrading.
  3. Ship the LD_PRELOAD shim and fake proc files inside the image until the fd/gVisor fixes for items 1–7 land; wire the five FDGV_* env vars in the entrypoint.
  4. Config: max_page_size = "huge", socket provider, 212992 socket buffers, unique name, real user.
  5. For backtest, pre-stage genesis, keys, a branch-compatible snapshot and the shredcap capture in the image or a read-only bind; run with --no-watch.
  6. Upstream candidates, roughly in order of payoff: gVisor MADV_WIPEONFORK no-op; fd single-node NUMA fallback; fd aligned-reserve on the shmem create path; gVisor procfs constants; then the 1 GiB-file EFAULT and the mlock panic as bug reports with the included repros.
